# ufodb_v0 ロードマップ

Union-Find（素集合データ構造）を核にしたDB。Rust製、CLI(REPL)、キーのみ管理。

## バージョニング方針

メジャーバージョンごとにリポジトリを分ける、という方針自体は維持する。ただし**ストレージ（永続化）・TCPサーバー化・ユーザーアカウント（TCP接続時のログイン用）・configファイル**の4機能は、当初v1（別リポジトリ）を想定していたが、v0（このリポジトリ）に前倒しして実装することに変更した（Phase 12〜15）。

- **v0（このリポジトリ）**: オンメモリのUnion-Find/DB機能に加え、上記4機能を含む。ただしTCPサーバー化・ユーザーアカウント・configファイルは「技術的に実現できることを確認する」ところまでが目的
- **v1（別リポジトリ）**: 任意のサーバーに置いて常時稼働させる本格的なサーバー運用はv1以降で行う（判明している課題は「v1（別リポジトリ）について」参照）。それ以外は、v0からさらに先の大きな方針転換が必要になった場合に検討する

このロードマップの「Phase」は基本的にv0（このリポジトリ）のスコープ。

### v0の実装方針

- v0ではまずアイデアを出して実装してみることを優先する。本当に必要な機能かどうかの取捨選択は、v1着手時に判断する
- v0の実装は作り込みすぎず、まず動くことを優先する。リファクタや`thiserror`のような便利クレートの導入は、v1移行のタイミングで検討する
  - ただし**セキュリティに関わる箇所（Phase 14のパスワード等の認証情報）はこの限りではない**。平文保存のような、後からのリファクタでは取り返しがつかない実装は、v0の時点から避ける

### v1着手のタイミング

明確なトリガー条件は設けない。v0を「作り切った」と感じたタイミングで着手を検討する、という主観的な判断に委ねる。

## Phase 1: Union-Findコア (`src/lib.rs` or `src/union_find.rs`)
データ構造:
- `HashMap<String, usize>` … キー → 内部インデックス
- `Vec<usize>` parent配列
- `Vec<usize>` rank または size配列（union by rank/size用）

実装する操作:
- `make_set(&mut self, key: &str)` … 未登録キーなら新しいグループとして追加。既存なら何もしない
- `find(&mut self, key: &str) -> Option<String>` … 代表元のキーを返す。path compression込み。存在しないキーは `None`
- `union(&mut self, a: &str, b: &str)` … 2つのグループを統合。存在しないキーは内部で `make_set` して扱う
- `same(&mut self, a: &str, b: &str) -> bool` … 同じグループか判定。`UnionFind::same` と名前を揃える。`unite` と異なり、未登録キーが渡されても `make_set` はせず、単に `false` を返す（SAMEは参照系の操作であり、呼ぶだけでデータが増えるのは直感に反するため）

設計判断ポイント（実装しながら決める）:
- ~~`find` の再帰 vs ループ実装（再帰は大量データでスタックオーバーフローの可能性あり → ループ推奨）~~ → union by sizeで木の高さがO(log n)に抑えられるため、再帰のままで問題なしと結論
- union by rank と union by size のどちらにするか → **決定: size**（後の「グループ一覧・グループサイズ」機能と相性が良い）
- 存在しないキーに対する挙動 → **決定**: `unite` は自動登録（`make_set`してから統合）、`connected` は登録せず `false`

単体テストで最低限カバーすべきケース:
- 単純な union → find で同じ代表元になる
- 推移的な union（a-b, b-c → a と c が connected）
- 未登録キーの find/connected
- 同じキーを2回 union しても壊れない（冪等性）
- path compression 後も find の結果が変わらないこと

## 既知の制約（v0＝このリポジトリではやらない・やれないこと）
- **削除・分割は直接サポートしない**: 古典的Union-Findは一度unionしたグループを分割する操作をサポートしない。Phase 6で「union履歴を保持しての組み直し（rebuild）」というワークアラウンドを実装する予定（詳細はPhase 6参照）。
- ~~永続化なし: プロセスを終了するとデータは消える。v1（別リポジトリ）で対応する。~~ → Phase 12でv0に前倒しして対応する
- **値（value）なし**: 要素はキーのみ。KVとして使いたくなったら拡張が必要（v0/v1どちらでやるかは未定）。
- **規模**: 動作確認は10万件（`N = 100,000`）規模まで。理論上はメモリが許す限り動作するはず（union by size + 経路圧縮により操作はならしO(α(n))で、キー数に対してほぼ線形にしかメモリを消費しないため）だが、それ以上の規模は未検証。

## Phase 5: DB / GROUP（2層構成にする）
`DB`（名前付きの`Ufdb`インスタンス）→ `GROUP`（代表元ごとに自動形成されるグループ。ユーザーが直接作るものではない）という2層構成にする。`USE`で切り替えるのは`DB`のみ。

- [x] データ構造: `HashMap<String, Ufdb>`（DB名 → `Ufdb`）を持つ層を、`union_find.rs`→`Ufdb`と同じレイヤリングで新規モジュール`src/db.rs`（`Db`構造体）に切り出した。フィールドは`current_db: String`（現在選択中のDB名）と`db: HashMap<String, Ufdb>`の2つ。`current(&mut self) -> &mut Ufdb`で選択中の`Ufdb`への可変参照を返す（`current_db`は常に`db`内の実在するキーを指す、という不変条件を`new`/`create_db`/`use_db`が維持する）
- [x] `CREATEDB <name>` コマンド: `Db::create_db(&mut self, name: &str) -> bool`。`db`に`name`が無ければ`Ufdb::new()`を挿入、あれば何もしない。**いずれの場合も`current_db`を`name`に切り替える**（新規/既存で非対称にしない）
- [x] `USE <name>` コマンド: `Db::use_db(&mut self, name: &str) -> bool`。`db`に`name`が存在すれば`current_db`を切り替えて`true`、存在しなければ**切り替えずに`false`**を返す（自動作成はしない）。`main.rs`側は`false`が返ってきたときだけ「DBが存在しません。作成しますか？(y/n)」と確認し、`y`なら`create_db`を呼ぶ（`SEED`の既存データ確認プロンプトと同じ役割分担: 存在判定と本来の切り替えは`Db`、ユーザーとの対話は`main.rs`）。当初想定していた「即エラー」より一段階親切な形に着地した
  - **Phase 13着手に伴い見直し（決定）**: `USE`コマンド自体を廃止する方針に変更した。詳細・理由はPhase 13参照
- [x] 起動時に名前付きのデフォルトDB（`ufdb`）を1つ用意し、最初からそれが選択された状態にしておく（PostgreSQLの`postgres`データベースに相当。`Db::new()`が`"ufdb"`キーで`Ufdb::new()`を1つ持った状態で初期化する）
- ~~設計判断ポイント: `USE`で存在しない名前を指定されたときに自動作成する（`make_set`と同じ自動登録方式）か、`CREATEDB`のような明示的な作成コマンドを別途用意するかを実装時に決める~~ → **決定**: 明示的な入力を優先し、`CREATEDB`を新設。`USE`は自動作成しない
- ~~設計判断ポイント（実装しながら決める）: `CREATEDB`に既存名を指定した場合の挙動（`make_set`のようにbool返却でno-opにするか、エラーにするか）~~ → **決定**: エラーにはせず、常にそのDBへ切り替える（＝`CREATEDB`は「新規なら作成」＋「常にUSEを兼ねる」の2ステップ。新規作成時も既存名指定時も、実行後は必ずそのDBが選択された状態になる。挙動が新規/既存で非対称にならない）

- **DBは互いに完全に独立**: 各DBは別々の`Ufdb`インスタンス（独自の`keys`・独自の`UnionFind`）なので、DBをまたいだ`MERGE`/`SAME`などは成立しない。UFQLのコマンドは常に「現在`USE`で選択中の1つのDB」だけを操作対象にする。DB間でデータを行き来させたい場合は、対象DBに`USE`で切り替えた上で改めて`INSERT`/`MERGE`し直す必要がある（自動的な相互参照・インポート機構はv0では持たない）

## Phase 6: 削除サポート（graphの再構築によるrebuild）
古典的Union-Findは分割・削除を直接サポートしないため、「実際にグループを統合した辺だけを持つ`graph`（Phase 11参照）から対象を除いて、`UnionFind`を一から組み直す」というワークアラウンドで対応する。

- [x] `graph`はPhase 11で`Ufdb`に追加する`HashMap<String, Vec<String>>`（実際に統合された辺のみを持つ全域木/森）をそのまま流用する。Phase 6独自の履歴構造は持たない
- [x] 削除実行時: 対象キー（またはUNMERGE対象の辺）を`graph`から取り除き、残った辺で新しい`UnionFind`を一から組み直す（`add`→`unite`を辺の集合に対して実行）。`graph`が閉路のない全域木/森であることが保証されているため、削除は「対象キーに触れる辺を除く」だけでよく、元の時系列順に再生し直す必要はない（連結性の最終結果は辺を足す順序に依存しないため）
  - 実装: `Graph::remove_edge`（`src/graph.rs`）と`Ufdb::unmerge`（`src/lib.rs`）。`UNMERGE <a> <b>`コマンドとして`main.rs`のREPLにも接続済み
- [ ] `DELETE <key>`（キー削除）: Phase 12で永続化が入り、誤って登録したキーを消せないとファイルに残り続けるため**必須**とする（当初の「スコープ外」から方針変更）
  - `UNMERGE`と同じく「`uf`は`graph`（実際につないだ辺の記録）から作り直せる」という考え方で、対象キーに触れる辺をすべて外してから組み直す。グループが分かれるかどうか（キーが木の途中か葉か）で処理を分けない。葉のキーでも、他のキーの`parent`がそのキーを代表元として指している可能性があり、`size`も変わるため、`uf`だけ直して済ませられない
  - `graph`側にノードの削除が必要: 対象キー自身のエントリーと、隣接するキーの隣接リストにある対象キーの両方を消す（現状の`Graph`には`remove_edge`しかない）
  - ~~設計判断ポイント: 削除後の`UnionFind`のインデックスに穴を残す（tombstone）か、全キーを振り直すか~~ → **決定**: 振り直す。組み直しの際に`reset()`（長さはそのまま）ではなく空の`UnionFind`から作り直し、残ったキーに0から連番を振り直してから辺を再生する。組み直し自体がO(E・α(E))かかるため、振り直しで増えるのはO(N)だけで、計算量はほぼ変わらない。穴を残す方式は削除のたびにゴミが増え、それが永続化ファイルにも書き出されるため採らない
  - 注意: `groups()`の戻り値のキー（代表元のインデックス）は振り直しで変わる（`unmerge`後に変わりうるのと同じ）。Studio・Playgroundがこの値を保存して使っていないことを確認する
- コスト: 削除1回あたり **O(E・α(E))**（`E`は`graph`が保持している辺の数、`α`は経路圧縮+union by sizeでのならし計算量）を許容する。頻繁な削除がボトルネックになるようなら、より効率的な削除可能データ構造への置き換えは将来の検討課題（v1以降）
- ~~設計判断ポイント（実装しながら決める）: 「削除」の対象は何か: 特定のキーをデータベースから完全に削除する（`DELETE <key>`）のか、特定の辺（過去の`MERGE`）だけを取り消す（`UNMERGE <a> <b>`的なもの）のか。`graph`が全域木/森になったことで、後者（特定の辺の削除＝木の枝刈り）も素直に扱えるようになった~~ → **決定**: `UNMERGE <a> <b>`（辺の削除）から着手する。`DELETE <key>`はキー削除後に`UnionFind`のインデックス（`Vec<usize>`、連番前提）へ穴を残すか全キーを振り直すかという追加の設計判断が必要で難易度が高い。`UNMERGE`はキーの集合（universe）自体は変わらないため、`graph`から対象の辺を1本除いて残りの辺で`UnionFind`を組み直すだけで済み、インデックスの振り直し問題が発生しない（`DELETE <key>`は後に必須化し、振り直し方式に決定。上記参照）
- Phase 5でDBが複数になったことで、`graph`は`Ufdb`ごと（＝DBごと）に独立して持つ状態が既に実現している（`Db`が`HashMap<String, Ufdb>`で各`Ufdb`を保持しており、`graph`は`Ufdb`のフィールドのため自動的にDB単位で分離される）

## Phase 8: EXPLAIN（dry run）

## Phase 9: STATS（統計情報）
既存のデータ（`keys`と`UnionFind`の`parent`/`size`）だけで計算できる、DB全体のサマリを表示するコマンド。どの項目を採用するかは未定（候補を列挙しておき、後で絞る）。

候補:

- グループ数（代表元の種類数。`GROUPS`と同じ走査で数えられる）
- 最大/最小/平均グループサイズ（`GROUPS`の結果から集計）
- 最大木の高さ（`find_readonly`（Phase 8）を使えば副作用なく実際の深さを測れる）
- Phase 6（削除サポート）実装後なら、保持しているunion履歴の件数

- 実装方針: `GROUPS`の集計ロジックを再利用してサマリだけ出す形が自然
- 位置づけ: v0スコープ（既存のオンメモリデータからの計算のみ、ストレージ不要）

## Phase 10: コマンドごとのメモリ使用量表示（カスタムアロケータ）
実行時間の表示と対になる機能。各コマンド実行の前後で、実際に確保・解放されたバイト数を表示する。

- [ ] `#[global_allocator]` で `System` アロケータをラップした独自アロケータを定義する（`GlobalAlloc`トレートを実装）
- [ ] `alloc`/`dealloc` の中で `AtomicUsize` のカウンタを加減算し、プロセス全体のアロケーション量を追跡する
- [ ] 各コマンド実行の前後でこのカウンタを読み取り、差分をナノ秒の実行時間表示と並べて表示する
- 注意点: これは**プロセス全体**のアロケーション活動を捉える。`println!`のフォーマットや`clap`のパースなど、`Ufdb`本体とは無関係な一時アロケーションのノイズも混ざる（実行時間表示における「OSタイマー精度は実際はナノ秒より粗い」という注意書きと同様の位置づけ）
- 設計判断ポイント（実装しながら決める）:
  - 表示するのは「正味の増減（確保 − 解放）」か、「確保したバイト数の総量（解放は無視）」か。一時的なVecなどはコマンド内で確保後すぐ解放されることもあるため、正味の増減だけだとほぼ0に見えるケースがある。何を見せたいかで設計が変わる

## Phase 11: HTML出力（静的なMERGE構造の一覧表示）
現状の`UnionFind`は経路圧縮によって`parent`が平坦化されるため、`parent`配列をそのまま辿ってもMERGEの実行履歴（どのキーとどのキーが直接繋がれたか）は復元できない。可視化用に、`UnionFind`の性能用データ（`parent`/`size`）とは別に「実際にグループを統合した辺」だけを保持する`graph`を`Ufdb`に追加する。この`graph`はPhase 6（削除）とも共有する（詳細はPhase 6参照）。

このリポジトリ（v0）で扱うのは静的なスナップショット出力のみ。動的な更新・編集・インタラクションはTauriアプリ側（別リポジトリ）の責務とし、ここでは実装しない。

- [x] `Ufdb`に`graph: HashMap<String, Vec<String>>`（キー→隣接キー一覧）を追加する。無向グラフとして両方向（a→b, b→a）を記録する
  - 実装は`src/graph.rs`に`Graph`構造体（`edges: HashMap<String, Vec<String>>`を1フィールドだけ持つラッパー）として切り出し、`Ufdb`は`graph: graph::Graph`を持つ形にした。`UnionFind`が`union_find.rs`にモジュール分離されているのと同じ扱い（別クレートにはしない。理由: `graph`は`Ufdb::unite`の履歴に依存するデータであり、`UnionFind`から独立していても`Ufdb`からは独立していないため）
- [x] `unite(key_a, key_b)`が呼ばれたとき、**戻り値が`true`（実際に2つのグループを統合できた）場合にのみ**`graph`にa-bの辺を追加する。すでに同じグループの場合（no-op、`false`）は辺を追加しない
  - これにより`graph`は常に閉路のない全域木/森（spanning tree/forest、重みなしなので「最小」ではない単純な全域木）になることが保証される。同じペアに複数回`MERGE`しても2回目以降はno-opなので辺が重複することもない
  - [x] 孤立ノード対応: `make_set`が新規キーを登録した分岐で`Graph::add_node(key)`を呼び、`graph`に空のVecのエントリを先に作っておく方式にした。`add_node`は`or_insert_with`で「無ければ作る・あれば何もしない」ため、その後の`add_edge`（`entry().or_insert_with(Vec::new).push(...)`）と衝突しない
- 残課題: `graph`（`Graph`の中身）を検証する結合テストは`main.rs`側にまだ書けない。理由は、現状のREPLに`graph`の中身を出力するコマンドが存在しないため（`GROUPS`はグループの中身は見せるが辺の情報は見せない）。SNAPSHOT（本Phase）か、何らかのSTATS/DEBUG系コマンドが`graph`を観測可能にしたタイミングで、`main.rs`側に結合テストを追加することを検討する。それまでは`Graph`単体のテスト（`src/graph.rs`内、`add_node`/`add_edge`の直接呼び出し）でカバーする
  - 考え方はKruskal法の閉路検出（`union-find.md`参照）と同じ: 「すでに繋がっている同士の辺は採用しない」ことで全域木を保つ
- ~~グラフの座標計算・SVG描画・大規模GROUPの閾値判定は行わない~~ → **方針転換（決定）**: 本命の可視化はTauri/React（別リポジトリ）に譲る。このリポジトリ（v0）でレイアウト計算まで作り込むのは二重投資と判断し、SNAPSHOTは大幅にスコープダウンする
- [x] `SNAPSHOT`: 現在の`graph`・`GROUPS`の状態をもとに静的なHTML文字列を組み立てる
  - **表示形式（決定）**: SVGでの座標計算はせず、各GROUPを`graph`のDFSで辿った**入れ子の`<ul><li>`リスト**として表示する（インデントで「誰と誰が直接MERGEされたか」という木構造が視覚的にわかる）
  - これにより`GROUPS`/CSV export（フラットなメンバー一覧のみ）との差別化になる。SNAPSHOTだけが`graph`の辺（実際のMERGE構造）を人間に見せる、という役割分担にする
  - 座標計算・レイアウトエンジンが不要なため実装コストは低い。`graph`が閉路のない全域木/森であることが保証されているので、DFSは各ノードを重複訪問せずに済む
  - **大規模GROUP対応（決定）**: サイズによる閾値判定はせず、**全GROUPを`<details>/<summary>`で初期状態は折りたたみ**にする（クリックで展開）。閾値の線引きが不要になり実装がシンプルになる
- **出力方式: サーバー起動+ブラウザ自動オープン（Storybook的な体験）**
  - `SNAPSHOT`はstdoutには出さず、常にローカルサーバーを起動してHTMLを配信し、`open`クレートでデフォルトブラウザにそのURLを開かせる
  - サーバーの生存期間は**1リクエスト分だけ**: GETリクエストを1回受けてHTMLを返したらリスナーを閉じ、REPLに制御を戻す（バックグラウンドで生かし続けない。マルチスレッドや`Ufdb`の共有状態管理が不要になり実装がシンプル）。最新化したい場合は改めて`SNAPSHOT`を呼び直す運用にする
  - 実装は`tiny_http`（軽量な同期HTTPサーバー、asyncランタイム不要）+ `open`（クロスプラットフォームでブラウザ起動）を使う。生の`TcpListener`でHTTPを手書きする案やactix/axumのようなフルフレームワークは見送る
  - これはPhase 7のCSV export（標準出力のみ、ファイルI/Oなし）とも、Phase 12のストレージ（ファイルへの永続化）とも異なる出力経路。ディスクに何も書き込まない・プロセス終了とともに消える一時的なTCPリスナーである点は変わらない
  - 新規依存として`Cargo.toml`に`tiny_http`・`open`を追加する
- ~~コマンド名（当初`EXPORT HTML`仮称）は未確定のまま~~ → **決定**: `SNAPSHOT`（1単語）に変更。他のコマンド（`INSERT`/`MERGE`/`SAME`/`GROUPS`/`SIZE`/`CREATEDB`/`USE`/`UNMERGE`/`SEED`/`EXIT`）が全て1単語で、`clap`の`rename_all = "UPPER"`もenumバリアント名（1単語）をそのままサブコマンド名にする仕組みのため、2語コマンドは一貫性・実装の単純さの両面で不利と判断。名前自体も「静的スナップショットのみを扱う」というPhase 11の設計意図と合っている
- Phase 6（削除）とはこの`graph`を共有する: 「実際にグループを統合した辺の全域木/森」という1つのデータで、可視化（本Phase）と削除時のrebuild（Phase 6）の両方を賄う

## Phase 12: ストレージ（永続化）

## Phase 13: TCPサーバー化
CLIのREPLプロセスと、別プロセスとで同じ「生きているデータ」を共有できるようにする。当初は「Tauri側と共有する必要が出てきたら検討する低優先度事項」としていたが、v0の正式な機能として前倒しする。

### `USE`コマンド廃止（Phase 5からの設計変更）
TCPサーバー化の検討過程で、「`USE`で動的にDBを切り替える」という運用自体がほとんど発生しないのでは、という疑問が出た。PostgreSQLを確認すると、`CREATE DATABASE`は自動でセッションを切り替えず、また接続の途中でDBを切り替える`\c`コマンドも実体は「接続を切って指定DBへ繋ぎ直す」という再接続であり、動的な切り替えという概念自体を持たない。この設計に倣うことにした。

- **決定**: `USE`コマンドを廃止する。DBを変えたい場合は繋ぎ直す（CLIなら再起動、TCPなら再接続）
- **決定**: REPLは起動時のCLI引数でDB名を指定する（例: `ufodb_v0 --db foo`。未指定時はデフォルトDB`ufdb`）。TCPは接続直後の最初のやり取り（ハンドシェイク）でDB名を指定する
- **決定**: ハンドシェイクはJSON等の構造化データにする（接続後の通常コマンドは文字列のままだが、ここだけ例外）。理由: Phase 14で認証情報（ユーザー名・パスワード）を追加する際、フィールドを増やすだけで対応できるようにするため
- **決定**: 指定されたDB名が存在しない場合は拒否する（自動作成はしない。エラーで起動/接続を失敗させる）。新しいDBを使いたい場合は、まず既存DB（例: デフォルトDB）に接続した状態で`CREATEDB`を実行してから、あらためてそのDB名を指定して繋ぎ直す
- **決定**: `CREATEDB`の挙動は変えない（Phase 5の決定どおり、作成後は自動でそのDBを使う状態になる）
- **決定**: 上記に伴い、`Db`構造体（現状`current_db: String` + `db: HashMap<String, Ufdb>`、[db.rs:6-9](../src/db.rs#L6-L9)）を「複数の入り口から共有される実データ本体（`HashMap<String, Ufdb>`）」と「各入り口（REPLプロセス自身、TCP接続それぞれ）がローカルに持つ『今使っているDB名』」に分離する構造変更が必要

### 並行アクセス制御
- **決定**: 共有する実データ本体は`Arc<Mutex<...>>`で丸ごと1つのロックとして囲む（DBごとの個別ロックはしない）
  - 理由: 「1接続ずつの逐次処理」のため、同時にアクセスするのは最大でもREPLスレッドとTCP処理スレッドの2箇所のみ。かつ各コマンドの処理はごく短時間（O(α(n))）で終わるため、粗い粒度のロックでも実用上の影響は小さいと判断した。個別ロック（`HashMap<String, Arc<Mutex<Ufdb>>>`等）は、DBの追加＝`HashMap`自体の構造変更と既存エントリへのアクセスの両立が必要になり実装が複雑化するため、v0では見送る

## 検討事項（未定）: ETTによる高速な削除
Phase 6のrebuild方式（O(E・α(E))）の代わりに、削除を**O(log n)**まで高速化できる案。森全体を1本のオイラーツアー系列として平衡二分探索木（splay木など）で持ち、`unite`（link）/削除（cut）/`same`（同じ木か判定）をすべてO(log n)で行う。

- 前提: 今の`unite`は同じグループならno-op（辺を作らない）ので、森に冗長な辺（サイクル）は発生しない。この前提がある限り、素のETTで「特定のMERGEの取り消し＝O(log n)」が実現できる（Phase 11の`graph`がこの前提を満たす具体的な実装になっている）
- 「辺を切った後も別の辺経由でまだ繋がっているか」まで扱う完全動的連結性が必要になった場合は、ETT＋辺のレベル分け（Holm–de Lichtenberg–Thorup算法など）が必要になり、コストもO(log²n)ならしまで上がる。より複雑
- `parent`/`size`の`Vec`2本というシンプルな今の実装を、平衡二分探索木ベースの実装に丸ごと置き換える必要があり、実装コストはPhase 6よりかなり大きい
- 位置づけ: Phase 1やPhase 6には組み込まず、あくまで学習用の検討事項として保留。着手するかは未定

## 検討事項（未定）: 独自のバイナリファイルフォーマット
Phase 12で採用したJSON（`serde_json`）の代わりに、ファイル内のバイトの並べ方を自分で設計する案。『Database Internals』3章（ファイルフォーマット）の学習を兼ねる。考え方の整理は`docs/design/`のスライド（`storage-layers` / `page-block-sector` / `file-format`）を参照。

- 動機: JSONは先頭から全部読まないと中身の位置がわからず、1件の変更でもファイル全体を書き直す。フォーマットを自分で決めれば、1件の変更で書く量を減らせる
- 候補は次の2つ。現時点の見立てでは**追記ログ方式**がufodbに合う（理由は後述の対比を参照。採用は未定）
  - **ページ方式**: ファイルを固定サイズのページに区切り、変更のあったページをその場で書き換える。RDBMSがB+木と組み合わせて使う方式
  - **追記ログ方式**（このドキュメントでの呼び名）: ファイルを「本体」（ある時点の全データ）と「追記ログ」（それ以降の変更の記録）で構成し、変更は末尾に足すだけにする。追記ログが溜まったら本体を作り直し、追記ログを空にする。Redisの「RDB（スナップショット）+ AOF（追記専用ファイル）」と同じ組み合わせ
- Phase 12との関係: Phase 12は「内部状態を人間が見える形で出す」方針からJSONを選び、速度が問題になった場合の移行先として`bincode`を挙げている。本項はそれとは別で、既存のシリアライズ形式に任せず、フォーマットそのものを設計する。JSONを置き換えるかどうかは未定（置き換える場合は既存の`.json`ファイルとの互換性・移行処理が別途必要）
- Phase 13（TCPサーバー化）とは並行して進められる: 保存形式を知っているのは`storage.rs`だけで、呼び出し側（`main.rs` / `db.rs`）は`storage::save` / `storage::load`の2関数しか使わない。Phase 13が触るのは`main.rs`と`db.rs`、本項が触るのは`storage.rs`とコア（`lib.rs` / `union_find.rs` / `graph.rs`）で、ほぼ重ならない。衝突を避けるため、新しいフォーマットは別モジュールとして作り、`storage::save`の中身はフォーマットが固まるまでJSONのままにする
- 位置づけ: 学習用の検討事項。Phase 12の決定（JSON）は変えない。着手・採用するかは未定

### ページ方式と追記ログ方式の対比

| 観点 | ページ方式 | 追記ログ方式 |
|---|---|---|
| ファイルの形 | 固定サイズのページの並び | 本体 + 末尾の追記ログ |
| ファイルに置くもの | 問いに答えるための構造（`parent`等）をそのまま置く | 元の情報だけ（キーの一覧と辺の一覧）。`parent`/`size`は置かない |
| 変更の書き方 | 該当するページをその場で書き換える | 末尾に記録を足す |
| 1件の変更で書く量 | ページ1枚（例: 8KB） | 数バイト〜（`MERGE`なら約9バイト） |
| 経路圧縮の影響 | 書き換わった`parent`のページを書き戻す。`SAME`のような調べるだけの操作でも書き込みが起きる | なし（`parent`がファイルにないため） |
| 一部だけ読む | できる | できない。起動時に全部読む |
| メモリに載らない規模 | 扱える | 扱えない |
| 起動時の処理 | 必要なページを読むだけ | 本体を読み、追記ログを適用し、辺を`unite`して`parent`/`size`を作り直す |
| 定期的に必要な作業 | 特になし | 本体の作り直し（ファイル全体を書く） |
| 合う問い | 「このキー、この範囲の行はどれか」（RDBMS） | 足すだけの操作が中心のデータ（Union-Find） |

- ページ方式がufodbに合わない理由:
  - `find`は`parent`を辿って配列の離れた位置を読むため、辿る先がどのページにあるかに規則性がない。B+木がRDBMSに合うのは、キーを並べて保つことで「キーが近いものを近くに置く」ことができ、問い合わせもキーの順で必要な場所が決まるから。Union-Findで一緒に読みたいのは同じグループのキーで、これは`MERGE`の履歴で決まり、`MERGE`のたびに変わる
  - 経路圧縮が読み取りを書き込みに変える（上の表のとおり）
  - 全体がメモリに載る限り、「一部だけ読む」利点が使われない
- 追記ログ方式がufodbに合う理由: 操作のほとんどが足すだけで済む（`INSERT`はキーが1つ増える、`MERGE`は辺が1つ増える）。例外は`UNMERGE`（辺が1つ減る）だけで、これも「辺を消した」という記録を足せば表せる
- ページ方式を選ぶ理由が出てくるのは、全体をメモリに載せる現在の方式をやめる場合。そのときは上の1点目（`find`の読む場所に規則性がない）が主要な論点になる

### 追記ログ方式の設計メモ

- 元の情報と、そこから作れる情報を分ける。ファイルに置くのは元の情報だけにする（2か所の内容が食い違う壊れ方をなくすため）
  - 元: キーの一覧（登録順）、実際にグループをつないだ辺の一覧
  - 作れる: `parent`/`size`（辺を順に`unite`すれば同じグループ分けになる）、キー → インデックスの対応（登録順がそのままインデックスになる）
  - 逆向き（`parent` → 辺の一覧）は作れない。経路圧縮後の`parent`は「いま誰の下にいるか」しか持たず、どの2つが`MERGE`されたかが残らないため
- 本体の形（案）: ヘッダー（識別用の数バイト、バージョン、キー数、辺数、チェックサム） → キーの位置表（キー数 × 固定幅。`i`番目のキーがキー本体の何バイト目から始まるか） → キー本体（全キーの文字列をつなげたもの） → 辺の一覧（辺数 × インデックス2つ）
  - キーの位置表は、『Database Internals』3章の「ページ内のレコードの位置の一覧」と同じ考え方。文字列の長さがばらばらでも、位置表が固定幅なので`i`番目のキーに掛け算でたどり着ける
  - 辺はインデックスで書く。現状のJSONでは、1つのキー文字列が`keys`・`graph`の見出し・隣のキーの一覧に重複して出る
- 追記ログの記録（案）: 「キーを足した」「辺を足した」「辺を消した」の3種類。`SAME`/`GROUPS`は記録しない
- Phase 12との関係: Phase 12は「`keys`と`parent`/`size`をそのまま保存する（案A）」を選び、`unite`の再生（案B）を再構築コストを理由に退けている。追記ログ方式は案Bに近く、採用する場合はこの決定を見直すことになる。再生にかかる時間はまだ測っていない（辺の数にほぼ比例するだけなので、ファイルを読む時間より短いという見込みはあるが、未検証）
- `SAVE`コマンドの意味が変わる: 操作のたびに追記するなら、明示的な`SAVE`はほぼ不要になる。残すなら「本体の作り直しを今すぐ行う」という意味にするかを決める
- 保存のコストは、書く量ではなく「いつディスクに届いたことにするか」で決まる: OSは書き込みをいったんメモリに溜めるため、追記の直後に電源が落ちるとその追記は消えうる。確実に残すにはOSに書き出しを頼む操作（`fsync`）が必要で、これは追記そのものよりずっと時間がかかる。頻度の候補は「操作のたび（失うものなし、遅い）」「一定間隔（その間隔分を失いうる）」「OS任せ（最も速い）」
- 本体の作り直しでは、元のファイルを直接上書きしない: 別名で書き終えてから名前を付け替える。書いている途中で落ちても元のファイルが残る。なお、現状の`storage::save`は`std::fs::write`で直接上書きしており、フォーマットとは無関係に同じ問題を持つ
- Phase 13との接点: Phase 13では共有データを`Arc<Mutex<...>>`で丸ごと囲むため、保存はロックを持ったまま行う。追記ログ方式なら、ふだんロックを持つのは数バイトの追記の間だけになる。本体の作り直しはファイル全体を書くので、その間の待ち時間をどうするかは別途決める

### フォーマットによらない設計判断ポイント

- 整数の幅は`usize`に合わせず固定する。`usize`は64ビット環境で8バイト、WASM（`wasm32`）で4バイトのため、そのまま書くと環境によってファイルの形が変わる
- 「`Ufdb` ⇔ バイト列」の変換と「バイト列 ⇔ ファイル」の読み書きを分ける。前者はOSの機能を使わないので、ファイルなしでテストでき（バイト列にして戻し、同じになるかを確かめる）、コア側に置いてもWASMビルドを妨げない。後者は`storage`の後ろに置く
- コアのフィールド（`parent` / `keys` / `edges`等）は非公開で、現状は`serde`のderiveが読み書きしている。自前でバイト列にするには、値を取り出す手段（アクセサを足すか、変換をそのモジュール内に置くか）を決める必要がある

### 本格的なサーバー運用（常時稼働）に向けた課題
v0のPhase 13〜15は技術検証が目的のため、任意のサーバーに置いて常時稼働させる際の課題はv1以降で対応する。現時点で判明しているもの:

- **標準入力が閉じるとプロセスごと終了する**: Phase 13ではREPLとTCPサーバーを同一プロセスに持たせる方針だが、REPLループは`while let Some(line) = lines.next()`で回っているため、systemdやDockerなど標準入力が閉じた環境で起動するとループが即終了し、`main`を抜けてTCPサーバーも止まる。REPLを起動しない「サーバー専用モード」（例: `--no-repl`のような起動オプション）が必要
- **認証なしのまま外部に公開しない**: Phase 13は認証なしで作るため、その段階では`127.0.0.1`のみで待ち受ける。Phase 14で認証を入れた後も、素のTCPではパスワードが平文でネットワークを流れるため、外部に公開するならTLS（またはSSHトンネル等）が必要
- **保存先ディレクトリの解決**: Phase 12で採用した`directories`クレート（`ProjectDirs`）はホームディレクトリの存在を前提にしており、ホームを持たないサービス用ユーザーで動かすと解決に失敗しうる。Phase 15のconfigファイルで保存先を明示指定できるようにすれば回避できる

## Web Playground（WASM、別リポジトリ）との連携メモ
Studio（Tauri）と同じUI・同じGUI操作をブラウザだけで提供するWebアプリ（`ufodb-playground`、別リポジトリ）。UIコンポーネントは別リポジトリのデザインシステム（`ufodb-design-system`）でStudioと共有する。

- 構成: `ufodb_v0`をWebAssemblyにコンパイルし、ブラウザのタブ内で`Ufdb`を動かす。DBサーバーもTCP接続も不要（サーバーは静的ファイルを配るだけ）。永続化もしない
- Playground側は`ufodb_v0`をgit依存で参照し、`#[wasm_bindgen]`で`Ufdb`を公開する薄いラッパーcrateを持つ（Studioの`#[tauri::command]`に相当）。ラッパーはPlayground側リポジトリの責務で、このリポジトリでは実装しない
- Playgroundが使うのはコア（`Ufdb`/`UnionFind`/`Graph`）のみ。`storage`/`db`はファイルI/O（`std::fs`）を使うためWASM上では呼ばない

### このリポジトリ側で必要な対応
- [ ] **lib単体をWASM（`wasm32-unknown-unknown`）でビルドできるようにする**: 現状は`cargo check --lib --target wasm32-unknown-unknown`が`open`クレートの`compile_error!`（`open is not supported on this platform`）で失敗する。`open`/`tiny_http`（`main.rs`の`SNAPSHOT`でしか使わない）は`[dependencies]`にあるため、libのビルドにも巻き込まれている。検証として、`src/`は一切変えずに`Cargo.toml`から`open`/`tiny_http`の2行を消したコピーではビルドが通ることを確認済み（`clap`/`directories`は残したままで通る）。つまりコアのコード自体はWASMでそのままコンパイルできる
  - 分け方は**feature方式**（`cli`/`storage`/将来の`server`などのfeatureに依存をまとめ、binに`required-features`を付ける。Playgroundは`default-features = false`で参照する）を想定。targetで分ける方式（`[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`）でもWASMビルドは通るが、Phase 13以降で増えるサーバー用の依存（非同期ランタイム等）がStudioを含むネイティブの利用者すべてでビルドされてしまうため、feature方式の方が将来の見通しが良い
  - 原則: コアのモジュールには、OSの機能（ファイル、ネットワーク、スレッド、時刻）を使うコードを入れない。それらはfeatureの後ろかbin側に置く（`std::time::Instant::now()`は`wasm32-unknown-unknown`でpanicする点にも注意）
- [ ] （任意）`sorted_groups() -> Vec<Vec<String>>`のような、グループをソート済み・所有権ありの形で返す公開APIを追加する: 現状はStudio（Tauriの`groups`コマンド）と`main.rs`の`GROUPS`がそれぞれ同じソート処理を書いており、Playgroundのラッパーでも同じ処理が必要になる。また`groups()`は借用（`HashMap<usize, Vec<&String>>`）を返すため、そのままではJSに渡せない
  - 2026-09-28時点で、Playgroundのラッパー（`wasm/src/lib.rs`）も同じ並べ替えを持つようになった（3か所目）。Playgroundでは、サイズが同じグループの順序も固定するため「サイズの降順 → 同じなら中身の昇順」にしている（Studioはサイズだけで比べており、同サイズのグループは`HashMap`の順序のまま入れ替わりうる）。`sorted_groups()`を作るときはこの条件に揃える
- [ ] `edges()`のような、グラフ（森）を「ノード一覧 + 辺一覧」の形で返す公開APIを追加する: Studio・Playgroundのグラフ表示に使う。内部の`Graph`は隣接リスト（`HashMap<String, Vec<String>>`）で、同じ辺をa側・b側の両方に持っているため、外から辺を1本ずつ列挙するには重複除去が要る。これは`Graph`の内部表現の都合なので、`Graph`側に持たせる
  - 2026-10-24時点で、Studioは`groups()` + `neighbors()`を組み合わせ、`key < neighbor`の組だけ残す形で`{ nodes, edges: [{ source, target }] }`を組み立てている（Studioの`graph`コマンド）。本体に入ったらそちらに置き換える
  - 決めること: 孤立ノード（INSERTしただけのキー）の扱い（Studioはノード一覧に含めている）、所有権ありの値（`String`）で返すか（JS・Tauriの境界では結局所有した値が要る）、順序の固定（Studioはノードをソートしている）。`groups()`は`&mut self`だが、こちらは`&self`で済む
- 設計判断ポイント: Phase 13で`Db`構造体を作り直す際、`Db`が永続化（`storage`）なしでも生成できる形にしておくと、将来Playgroundで複数DB（`CREATEDB`等）を扱いたくなった場合に流用できる。現状の`Db::new`は`dir: &Path`を受け取ってstorageからロードするため、永続化と結びついている
